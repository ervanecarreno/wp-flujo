## gb-global-styles

**Resumen.** GenerateBlocks separa claramente dos capas: (1) los atributos de bloque individuales, serializados como JSON dentro del comentario HTML de WordPress (con escapado automático de '--', '<', '>', '&', '\"' cuando el guardado pasa por el serializador estándar de WordPress), y (2) 'Global Styles', que es una funcionalidad EXCLUSIVA DE PRO (no existe en la versión free 2.x) implementada como un custom post type propio (reescrito por completo en la v1.7.0, sin ruta de migración automática desde el sistema legacy). Cada Global Style es una clase CSS reutilizable: se define una vez y todos los bloques que llevan esa clase heredan el cambio. Patterns (antes 'Local Templates') ahora usa el post type nativo de Patrones de WordPress core (wp_block) con taxonomías añadidas por GenerateBlocks; se exportan/importan vía Tools>Export/Import de WordPress o vía la pantalla 'Manage Patterns', y si un patrón lleva asociado un Global Style que no existe en el sitio destino, GenerateBlocks lo importa automáticamente. GenerateCloud (add-on de pago independiente, ~$99/año, incluido en GeneratePress One) permite alojar una librería de patrones en un sitio propio y conectarla a otros sitios por dominio + clave pública -- pero, según su documentación, 'a día de hoy una clave solo puede servir patrones', no Global Styles de forma directa (aunque llegan indirectamente si van adjuntos a un patrón). En 2.6 (junio 2026) GenerateBlocks Pro añadió edición de CSS 'a mano' (raw) tanto para bloques individuales como para Global Styles con soporte de Dev Tools, pero no encontré documentación que precise si ese CSS crudo vive fuera del JSON del atributo 'styles' o sigue las mismas reglas de escapado.

### Hallazgos

- **[alta]** Global Styles es una colección de clases CSS reutilizables cargadas globalmente: se crea una clase, se le añaden estilos, y se reutiliza en cualquier bloque; un cambio en la clase se propaga a todo el sitio.
  - *Fuente:* https://docs.generateblocks.com/article/global-styles-overview/ y https://docs.generateblocks.com/article/creating-a-global-style/
- **[alta]** Global Styles es una funcionalidad exclusiva de GenerateBlocks Pro; la versión gratuita (actualmente 2.4.1) NO la incluye -- solo tiene el 'styles builder' local, sin la capa de reutilización global.
  - *Fuente:* https://wordpress.org/plugins/generateblocks/ y https://generatepress.com/generateblocks-2-0-a-new-era/ (vía búsqueda)
- **[alta]** El sistema actual de Global Styles (introducido en Pro 1.7.0) fue una reescritura completa del sistema legacy, y GenerateBlocks declara explícitamente que NO hay migración automática entre ambos: hay que recrear las clases a mano.
  - *Fuente:* https://docs.generateblocks.com/article/migrating-from-legacy-global-styles/
- **[alta]** Cada Global Style se comporta como un selector CSS principal (una clase, p.ej. '.my-style') con selectores adicionales predefinidos (hover, links, icon) y un constructor de selectores avanzado ('More') para casos custom.
  - *Fuente:* https://docs.generateblocks.com/article/style-selectors/
- **[alta]** Tanto 'Global Styles' como 'Local Patterns' (Patrones) son custom post types de WordPress, por lo que en teoría son exportables/importables con el exportador/importador nativo de WordPress (Tools > Export / Tools > Import) como XML, igual que cualquier otro post type.
  - *Fuente:* https://generate.support/topic/export-global-styles-classes/ , https://generate.support/topic/export-import-global-styles/
- **[media]** GenerateBlocks Patterns usa el post type nativo de Patrones de WordPress core (el mismo que los bloques reutilizables/patrones sincronizados de Gutenberg), con taxonomías propias añadidas para gestionar 'Pattern Libraries'.
  - *Fuente:* resultado de búsqueda que cita generatepress.com/build-consistent-pattern-library-generateblocks-pro-generatepress/ (no pude verificar el texto exacto con WebFetch directo)
- **[media]** Al importar un patrón, si ese patrón usa un Global Style que aún no existe en el sitio consumidor, GenerateBlocks lo crea/importa automáticamente junto con el patrón (así lo confirma un representante de GenerateBlocks en el foro).
  - *Fuente:* https://generate.support/topic/generatecloud/
- **[media]** No existe una API REST documentada ni comando WP-CLI oficial de GenerateBlocks para exportar/sincronizar Global Styles o Patterns; los propios usuarios piden esto como feature request y algunos montan flujos caseros con wordpress-importer + hooks en save_post para versionar en git.
  - *Fuente:* búsqueda sobre generate.support y generatepress.com/forums (varios hilos), sin una página oficial única que lo confirme
- **[alta]** GenerateCloud es un add-on de pago separado (~$99/año, incluido en el bundle GeneratePress One) que permite alojar tu propia librería de patrones en un sitio WordPress público y conectar otros sitios a ella mediante dominio + clave pública.
  - *Fuente:* https://learn.generatepress.com/blocks/block-guide/getting-started-generateblocks/generateblocks-pro/generatecloud/ y https://generatepress.com/introducing-generatecloud-your-personal-wordpress-pattern-cloud/ (vía resultados de búsqueda)
- **[media]** La documentación oficial de GenerateCloud afirma explícitamente: 'a día de hoy, una clave solo puede servir patrones' (no Global Styles de forma independiente).
  - *Fuente:* https://docs.generateblocks.com/article/using-generatecloud/
- **[alta]** GenerateBlocks Pro 2.6 (lanzado ~23 junio 2026) añadió edición de CSS 'a mano' (raw) tanto para bloques individuales como para Global Styles, con soporte de Dev Tools del navegador y un atajo 'Edit CSS' en la barra de herramientas del bloque.
  - *Fuente:* https://generatepress.com/generateblocks-pro-2-6-brings-forms-and-styles-editing/
- **[baja]** No encontré ninguna fuente que documente si ese CSS crudo de 2.6 vive fuera del JSON del atributo 'styles' (evitando así el problema de escapado) o si sigue las mismas reglas; la documentación oficial no lo especifica.
  - *Fuente:* sin fuente -- ausencia confirmada tras varias búsquedas dirigidas
- **[media]** El serializador estándar de bloques de WordPress (usado también por GenerateBlocks) aplica 5 sustituciones de escape a los valores string dentro del JSON embebido en el comentario de bloque: '--' -> '--', '<' -> '<', '>' -> '>', '&' -> '&', '"' -> '"'. Esto significa que, SI el guardado pasa por el editor de bloques normal (o por cualquier código que use el serializador oficial de @wordpress/blocks), un literal 'var(--color)' dentro de un valor de estilo SÍ se escapa correctamente y NO rompe el comentario HTML.
  - *Fuente:* https://github.com/wpgaurav/generateblocks-skills/blob/main/skills/generateblocks-layouts/SKILL.md (fuente de terceros, no documentación oficial de GenerateBlocks/WordPress; no lo pude contrastar contra el código fuente oficial de @wordpress/blocks ni contra documentación oficial de GenerateBlocks)
- **[baja]** Esto matiza -- pero no anula -- la lección del proyecto Aridane: el problema de '--' rompiendo el comentario HTML aparece específicamente cuando el marcado se genera/pega a mano como texto plano (fuera del flujo de guardado normal del editor, que es como trabaja el usuario: 'marcado de bloques pegable'), porque entonces nadie aplica el escapado -- por ti. Si se escribiera var(--color) tal cual en el JSON pegado, sin escapar manualmente los guiones, seguiría siendo un riesgo real en ese flujo de trabajo concreto.
  - *Fuente:* inferencia propia a partir del hallazgo anterior, NO confirmada con una fuente que describa el comportamiento exacto del parser de bloques de WordPress ante un '--' sin escapar dentro de un comentario pegado directamente (sin pasar por el editor)
- **[alta]** GenerateBlocks emite al menos una variable CSS propia en el CSS compilado (fuera del JSON, en una hoja de estilos normal): '--gb-container-width', añadida en la v2.0.0 para exponer el ancho máximo global.
  - *Fuente:* https://wordpress.org/plugins/generateblocks/ (changelog)
- **[media]** El CSS 'compilado' de cada bloque (atributo 'css') es una hoja de estilos normal, no JSON -- solo el atributo 'styles' (la fuente editable) vive dentro del JSON del comentario. Esta distinción 'styles es la fuente editable; css es su caché compilada' es la que hace que el validador Node del usuario (reconstruir css desde styles) tenga sentido como capa de verificación.
  - *Fuente:* https://github.com/wpgaurav/generateblocks-skills/blob/main/skills/generateblocks-layouts/SKILL.md (fuente de terceros, no oficial)

### Recomendacion del investigador

1) Para el nuevo setup, asumir que Global Styles y Local Patterns son custom post types de WordPress: la vía de sincronización entre entornos MÁS FIABLE y sin coste extra es exportar/importar vía Tools>Export/Import (XML) o vía 'Manage Patterns', comprobando cada vez a mano que el import realmente registra los estilos (hay reportes de que a veces no se activan solos tras importar). 2) NO dar por sentado que var(--wp--preset--color--x) funciona dentro de un valor de Global Style solo porque teóricamente el serializador de WordPress escapa los '--'; antes de construir el flujo de trabajo alrededor de esto, hacer una prueba mínima real: crear un Global Style con var(--wp--preset...) como valor DESDE la propia UI de GenerateBlocks Pro, guardar, inspeccionar el HTML del comentario de bloque resultante (¿aparece \\u002d\\u002d o '--' literal?) y comprobar que no se rompe nada en frontend. Si el flujo de trabajo del usuario sigue siendo 'generar marcado pegable a mano' (no usar la UI), ese escapado automático NO se aplica solo, así que seguiría siendo más seguro seguir usando colores/valores literales en el marcado que se pega, y reservar var(--wp--preset...) solo para lo que se escriba DENTRO de la UI de Global Styles o del nuevo editor de CSS raw de Pro 2.6 (donde sí hay más margen para probarlo). 3) Considerar la limitación de guiones en el editor 'Edit CSS' de Pro 2.6 como zona no verificada: antes de apoyarse en ella para centralizar colores, hacer la misma prueba mínima descrita arriba. 4) GenerateCloud solo tiene sentido si el usuario gestiona MUCHOS sitios de cliente con librería de patrones compartida y está dispuesto a pagar ~$99/año adicionales y mantener un sitio 'cloud' público; para un flujo simple de un ayuntamiento/pyme puntual, exportar/importar XML manualmente es más barato y suficientemente fiable. 5) Dado que ninguna de estas piezas (Global Styles export, Patterns export, CSS raw de 2.6) tiene API REST o WP-CLI oficial, seguir tratando el validador Node propio (comparar 'styles' reconstruido contra 'css') como la pieza de mayor valor del flujo -- eso no cambia con esta investigación, y de hecho se refuerza: es la única verificación automatizable que no depende de que WordPress haga bien su parte.

### Verificacion adversarial

**DUDOSAS:**
- La nota sobre el escapado de '--' representa la sustitución como "'--' -> '--'" (es decir, sin cambio visible). Es engañosa/incorrecta tal como está escrita: el serializador de bloques de WordPress (serialize_block_attributes) sustituye '--' por la secuencia unicode-escapada '\\u002d\\u002d' (no por '--' literal), precisamente para que el guion doble no rompa el comentario HTML. Lo mismo aplica a las otras 4 sustituciones citadas ('<','>','&','"'): en WordPress real se convierten a secuencias \\u003c, \\u003e, \\u0026 y \\u0022, no a sí mismas. La conclusión práctica del agente (que el editor estándar sí escapa '--' de forma segura) es correcta en el fondo, pero la notación concreta que ofrece como 'prueba' es errónea y podría confundir si alguien la usa literalmente para verificar el HTML.
- La afirmación 'no hay migración automática... hay que recrear las clases a mano' es una simplificación excesiva. La documentación oficial (docs.generateblocks.com/article/migrating-from-legacy-global-styles/) describe una opción semi-automática: al crear un nuevo Global Style se puede elegir 'Copy the local block styles', que copia automáticamente los valores del Global Style legacy al nuevo. Lo único manual es (a) aplicar la nueva clase a los bloques existentes y (b) sustituir el Global Style legacy por el nuevo en el contenido. El propio doc también aclara que los Global Styles legacy NO desaparecen y siguen funcionando indefinidamente en paralelo, algo que el resumen del agente no menciona y que cambia el nivel de urgencia/riesgo de la migración.
- Hay una contradicción real entre dos fuentes oficiales de GenerateCloud que el agente detectó solo parcialmente: la página de marketing (generatepress.com/cloud/) dice explícitamente 'Build your go-to patterns and global styles once, and share them everywhere', mientras que la documentación técnica (docs.generateblocks.com/article/using-generatecloud/) dice 'As of right now, a key can only provide patterns.' El agente citó solo la segunda fuente (correcta técnicamente) pero no señaló que la propia web comercial de GeneratePress afirma lo contrario, lo cual es relevante para no fiarse ciegamente del marketing al planear el flujo de trabajo.
- La versión de GenerateBlocks Pro documentada como 'la más reciente' (2.6, junio 2026) ya no es la última a fecha de hoy (27 agosto 2026): existe GenerateBlocks Pro 2.7.0 (28 julio 2026), confirmada en fuente oficial generatepress.com/generateblocks-pro-2-7-0/ (no solo en el sitio pirata gplchimp.com que el agente descartó). 2.7.0 requiere GenerateBlocks (free) 2.4.0 como mínimo, lo cual es coherente con que la free stable actual sea 2.4.1, pero cualquier recomendación basada en '2.6 es lo último' está desactualizada en al menos una versión menor.

## theme-json-tokens

**Resumen.** GeneratePress (clásico) y GenerateBlocks tienen sistemas de color separados: GP expone sus Global Colors como variables CSS normales (--accent, --contrast...) usables en cualquier CSS real, pero GenerateBlocks resuelve siempre los colores a HEX literal dentro del atributo 'styles' de cada bloque — confirmado directamente por soporte oficial de GenerateBlocks — así que theme.json nunca controla el color final de un bloque GB, pase lo que pase. Hay un desajuste de breakpoints real y documentado oficialmente (GP=768px vs GB=767px por defecto), corregible con el filtro `generateblocks_media_query`, pero JS y el propio menú de GP hay que sincronizarlos aparte, a mano, contra un único origen. Para Figma→WordPress existe herramienta real y mantenida (10up, en GitHub, marcada beta) pero exige tema de bloques, algo que GP clásico no es — así que theme.json exportado de Figma sirve como archivo de tokens de referencia, no como control directo del sitio. La única vía verificada para evitar editar 100 KB de marcado al cambiar un color es sacar el color del bloque GB (que siempre lo resuelve a HEX) y moverlo a clases CSS reutilizables definidas en una hoja de estilos real del tema hijo.

### Hallazgos

- **[alta]** GeneratePress es un tema clásico (no de bloques) y, según su propio soporte oficial, un theme.json colocado en un tema hijo de GP es ignorado tanto en frontend como en el editor. GP no incluye theme.json propio y usa su propio sistema de 'Global Colors' vía Customizer.
  - *Fuente:* https://wordpress.org/support/topic/does-generatepress-support-theme-json-files/ y https://generatepress.com/forums/topic/creating-style-variations-in-child-themes-does-generatepress-have-a-theme-json/
- **[media]** Contradiciendo lo anterior (o matizándolo): WordPress Core SÍ soporta oficialmente theme.json en temas clásicos desde WP 5.8+ para registrar paleta de color del editor, tamaños de fuente, 'settings.custom' (que genera variables --wp--custom--*), etc. La documentación oficial dice que los settings/estilos de theme.json 'se reflejan tanto en el frontend como en los editores integrados de WordPress', aunque un tutorial específico matiza que las STYLES visuales del frontend clásico siguen viniendo de style.css.
  - *Fuente:* https://learn.wordpress.org/tutorial/using-theme-json-with-classic-themes/ y https://developer.wordpress.org/themes/global-settings-and-styles/introduction-to-theme-json/
- **[alta]** Los 'Global Colors' de GeneratePress (Customizer > Colors) SÍ se emiten como variables CSS estándar, legibles y usables libremente en CSS normal: --contrast, --contrast-2, --contrast-3, --base, --base-2, --base-3, --accent. Un tema hijo puede referenciarlas directamente en su propio CSS (ej. body{color:var(--contrast)}), y esto NO tiene el problema de '--' porque vive en una hoja de estilos real, no en el comentario HTML de un bloque.
  - *Fuente:* https://generatepress.com/forums/topic/theme-defaults-override-in-child-theme-for-colour-vars/
- **[alta]** GenerateBlocks (confirmado por soporte oficial de GenerateSupport, respuesta directa de un desarrollador) NO guarda referencias var(--color) cuando eliges un color en el selector: siempre resuelve el valor a un HEX literal en el atributo 'styles' del bloque, incluso si el color viene de theme.json o de Global Colors de GP. Cita textual: 'not yet, as the way core handle CSS colors variables (which is terrible) is not compatible with our color picker.'
  - *Fuente:* https://generate.support/topic/css-variables-from-theme-json-for-colour/
- **[alta]** GeneratePress (tema) usa por defecto el breakpoint móvil en 768px (por compatibilidad histórica) mientras que GenerateBlocks fue diseñado con 767px como 'fresh start'. Estos dos valores NO se sincronizan automáticamente entre sí; existe un hilo oficial de soporte de GeneratePress documentando exactamente este desajuste.
  - *Fuente:* https://generatepress.com/forums/topic/gp-gb-breakpoints/
- **[alta]** Los breakpoints de GenerateBlocks V2 por defecto son: desktop = min-width:1025px, tablet = max-width:1024px (tablet_only = 768–1024px), mobile = max-width:767px. Son configurables globalmente vía el filtro PHP `generateblocks_media_query` (claves: desktop, tablet, desktop_tablet, tablet_only, mobile) en functions.php; el cambio solo afecta a los estilos que se generen después, no reescribe el CSS ya existente.
  - *Fuente:* https://generatepress.com/forums/topic/generateblocks-breakpoints/ y https://generate.support/topic/custom-break-points/
- **[media]** theme.json no tiene ninguna clave nativa de 'breakpoints' responsivos (no existe settings.breakpoints); su bloque 'layout' solo define contentSize/wideSize, no anchos de media query. Esto es coherente con lo verificado sobre GB y con el conocimiento general del schema de theme.json, pero no llegué a inspeccionar exhaustivamente la referencia completa de developer.wordpress.org línea por línea para descartar al 100% alguna clave experimental nueva en 2026.
  - *Fuente:* inferido de developer.wordpress.org/themes/global-settings-and-styles/ (no se encontró ninguna clave de breakpoints en la documentación ni en las búsquedas realizadas)
- **[alta]** Existe un plugin de Figma mantenido por la agencia 10up, 'figma-to-wordpress-theme-json-exporter', que convierte Variables de Figma (color y números) en un theme.json real, incluyendo variantes de estilo y variables responsive Desktop/Mobile. Está marcado como 'Beta' por sus propios autores ('not sure what our ongoing support level for this will be') y, crucialmente, REQUIERE que el tema destino sea un tema de bloques (theme.json-based) para que ese theme.json tenga efecto — no está pensado para temas clásicos como GeneratePress.
  - *Fuente:* https://github.com/10up/figma-to-wordpress-theme-json-exporter
- **[baja]** También existen otros plugins de Figma community para exportar a theme.json o a JSON estilo Style Dictionary ('Theme.json generator - Wordpress', 'WP theme-json Converter', 'Variables to JSON'), y Tokens Studio ofrece @tokens-studio/sd-transforms para integrarse con Style Dictionary genérico. Ninguno de estos fue verificado a fondo (solo aparecieron en resultados de búsqueda, no los abrí uno por uno) y no encontré ningún transform de Style Dictionary oficial que genere específicamente el formato theme.json de WordPress — habría que escribirlo o adaptarlo.
  - *Fuente:* resultados de búsqueda web, listados en https://www.figma.com/community/plugin/1646140206187798360/theme-json-generator-wordpress y https://docs.tokens.studio/transform-tokens/style-dictionary (contenido no verificado con WebFetch)
- **[baja]** GenerateBlocks Pro 2.6 (release identificado como 'alpha' en la propia web de GeneratePress) introdujo un 'CSS Editor' / 'CSS Mode' que da acceso directo a escribir CSS crudo detrás de cualquier bloque o Global Style, en vez de solo el panel visual. Pero según la propia documentación sigue operando sobre el mismo 'styles object' que ya se serializa en el atributo del bloque — no encontré confirmación de que esto resuelva el problema de '--' dentro del comentario HTML, ni de que soporte var() de forma general (solo hay evidencia puntual de que var(--gb-container-width) se usa para el ajuste de ancho máximo).
  - *Fuente:* https://generatepress.com/write-any-css-you-want-introducing-the-css-editor/ y https://generatepress.com/generateblocks-pro-2-6-brings-forms-and-styles-editing/

### Recomendacion del investigador

Arquitectura concreta de fuente única de verdad para el próximo proyecto GP+GB:

1) Un único archivo de tokens (JSON, con forma tipo theme.json/Tokens Studio) como fuente de verdad editorial — a mano o exportado de Figma con el plugin de 10up (aceptando que su output theme.json solo sirve tal cual si migras a tema de bloques; con GP clásico, ese theme.json se usa como INSUMO, no como archivo que WordPress vaya a aplicar por sí solo).

2) Un script pequeño (PHP, ejecutado en build o en un mu-plugin) que LEE ese único JSON y genera, de forma automática, tres salidas — nunca copiar valores a mano en tres sitios:
   a. Los 7 Global Colors de GP (--contrast, --contrast-2/3, --base, --base-2/3, --accent) vía los filtros `generate_option_defaults`/`generate_color_option_defaults`, para que el Customizer y el token file jamás diverjan.
   b. Un theme.json real en el tema hijo (para aprovechar lo que WP Core sí procesa en temas clásicos: paleta del editor, settings.custom) — pero TRÁTALO como beneficio secundario para la UI del editor, no como control real del frontend, y VERIFÍCALO empíricamente en el sitio real (ver #4) antes de confiar en él, exactamente por la lección 1 del proyecto Aridane.
   c. Las mismas cifras de breakpoint inyectadas simultáneamente en: el filtro `generateblocks_media_query` (para que los bloques GB usen esos valores), un `wp_add_inline_script` con `window.SITE_BREAKPOINTS` (para que el JS del carrusel/menú lea el mismo número), y si usas el menú/nav nativo de GP, revisa su propio filtro de breakpoint (no lo verifiqué, hazlo contra la documentación de GP antes de asumir que coincide).

3) Para el problema central (d) — cambiar un color de marca no debe ser un search&replace en 100 KB de marcado GB — la única vía confirmada y segura es NO fijar el color como literal dentro del atributo 'styles' de cada bloque (GB siempre lo resuelve a HEX ahí, confirmado por su propio soporte). En su lugar: define un puñado de clases utilitarias (.text-accent, .bg-accent, .border-accent...) UNA vez en el CSS complementario del tema hijo (hoja de estilos real, no comentario de bloque) usando var(--accent) etc., y aplícalas a los bloques vía el campo de 'CSS classes' de GB en lugar de elegir el color en el panel visual. Cambiar la marca pasa a ser una edición en un archivo CSS de un puñado de líneas, no una búsqueda a ciegas.

4) Extiende el validador Node que ya construiste en el proyecto Aridane para que además: (i) falle si aparece un HEX de marca literal fuera de la lista de excepciones conocidas dentro del atributo 'styles' de un bloque, y (ii) en un entorno de staging real, compruebe si las variables --wp--preset--color--* / --wp--custom--* aparecen en el <style id="global-styles-inline-css"> del frontend — así conviertes la incertidumbre marcada arriba (si GP realmente ignora theme.json o no) en un hecho verificado contra tu propio servidor, no contra documentación contradictoria.

5) No apuestes el proyecto al CSS Editor de GenerateBlocks Pro 2.6: a fecha de esta investigación seguía marcado como alpha y no hay confirmación de que resuelva el bug de '--' en el comentario HTML. Trátalo como algo a vigilar, no como la solución actual.

## figma-handoff

**Resumen.** El Figma Dev Mode MCP Server ya no es solo beta: la lectura de contexto de diseño (código, capturas, metadata, variables) es de acceso general en todos los planes, pero con dos capas de fricción real para un freelance con clientes pequeños: (1) get_variable_defs -la herramienta que extrae design tokens- solo funciona en el servidor de escritorio local con un asiento de pago Dev/Full, y (2) el límite de uso se ata al plan del ARCHIVO propietario, no al tuyo, así que un cliente en Figma gratuito te deja con apenas 6 llamadas al mes sobre su archivo aunque tú pagues Professional. La alternativa REST API con personal access token es gratis de generar y cubre /files, /nodes, /images sin problema, pero el endpoint de Variables está reservado explícitamente a "full members of Enterprise orgs" -un plan a medida, fuera del alcance típico de un ayuntamiento o una pyme. Ni el MCP ni la REST API resuelven los dos bugs que más te costaron en el proyecto de Aridane (rutas de imagen en subdirectorio, breakpoints CSS/JS desincronizados), y tampoco evitan tener que aplanar las variables a literales porque GenerateBlocks V2 no admite var(--color) en el JSON del bloque. Con esos datos, diseñar directamente en HTML y usar Figma solo como capa de comunicación visual con el cliente (no como fuente de datos para el código) parece más fiable que montar un pipeline de extracción que depende del plan de pago que tenga cada cliente.

### Recomendacion del investigador

Para tu caso (freelance/estudio pequeño, clientes ayuntamientos/pymes, stack fijo GeneratePress + GenerateBlocks Pro V2 + ACF), mi recomendación es: NO montes un pipeline Figma MCP/REST → código como fuente de verdad para producción. Razones concretas:

1. La pieza que más te interesaría automatizar -Variables/design tokens- está bloqueada por plan: la REST API de Variables exige que el ARCHIVO viva en una organización Enterprise (precio a medida, pensado para empresas grandes), y tus clientes (ayuntamientos, pymes) casi nunca van a tener eso. La vía MCP evita el muro de Enterprise pero solo si usas el servidor de escritorio local (no el remoto) con un asiento Dev/Full de pago -y aun así, si el ARCHIVO que te entrega el cliente vive en un Figma gratuito (lo más probable con estos clientes), quedas capado a 6 llamadas al mes sobre ese archivo, sin importar tu propio plan de pago. Esto convierte "pedirle a Javier el Figma del cliente" en una lotería según el plan que tenga el cliente, justo el tipo de sorpresa de entorno que ya te costó caro en el proyecto de Aridane.

2. Aunque consiguieras extraer las variables limpiamente, tienes que volver a aplanarlas a literales de todos modos, porque GenerateBlocks V2 no admite var(--color) dentro del JSON del comentario de bloque (lección 4 de tu propio proyecto). Es decir: el problema de "colores repetidos 100 veces" NO lo resuelve Figma ni su MCP -es una limitación de tu stack de destino-, así que el paso Figma añade una capa de fricción (autenticación, rate limits, un servicio externo que puede fallar) sin resolver tu dolor real.

3. Tus dos incidentes más caros del proyecto de referencia (rutas de imagen rotas en subdirectorio, breakpoints CSS/JS desincronizados) tampoco los habría evitado ningún dato que venga de Figma: son bugs de traducción marcado→entorno y de falta de fuente única de verdad para breakpoints, que existen igual si el diseño nace en Figma o directamente en HTML.

Conclusión accionable: diseña directamente en HTML/CSS (tipo Claude Design) como prototipo navegable, y resérvate Figma solo para el momento en que el cliente (una alcaldía, por ejemplo) necesite comentar visualmente sobre una maqueta -en ese caso, una captura de pantalla o un PDF exportado del propio prototipo HTML sirve igual y no requiere ni token ni MCP. Si en algún proyecto puntual SÍ recibes un Figma ya armado por un diseñador externo con buen uso de Variables y el cliente SÍ está en Organization/Enterprise, entonces el MCP de escritorio (get_design_context + get_variable_defs + get_screenshot) es la vía más barata en fricción -pero trátalo como una fuente de referencia visual, nunca como el marcado final: sigue pasando cada bloque generado por tu validador Node de Aridane antes de pegarlo en producción.

## wp-git

**Resumen.** Investigué versionado de WordPress con fuentes oficiales (advancedcustomfields.com, developer.wordpress.org, wpengine.com/Local) y práctica establecida de la comunidad. El consenso es: versionar solo código propio (tema hijo, mu-plugins, plugin propio de CPTs, acf-json, patterns como PHP) y dejar fuera core/uploads/plugins de terceros. Local WP no tiene integración git nativa — hay que iniciar el repo a mano dentro de wp-content vía su terminal integrado. El problema de fondo persiste: el CONTENIDO real (páginas, opciones, y sobre todo los Global Styles de GenerateBlocks) vive en la base de datos como custom post types, y ninguna herramienta lo hace realmente 'diffable' en git — WP-CLI y los plugins de migración mueven snapshots completos, no versionan. ACF Local JSON sí resuelve la parte de los grupos de campos, y funciona en la versión gratuita de ACF (no es exclusivo de PRO). Para Custom Post Types, el consenso es registrarlos por código en un plugin propio/mu-plugin, nunca en el tema, por portabilidad.

### Hallazgos

- **[alta]** Práctica establecida: en un repo WordPress se versiona solo el tema hijo, mu-plugins propios y plugins custom desarrollados a medida; se excluyen (gitignore) el core de WordPress, wp-content/uploads, wp-config.php, cache y logs. Un enfoque frecuente es poner la raíz del repo git en wp-content/ (no en la raíz del sitio) para dejar wp-admin/wp-includes fuera por completo.
  - *Fuente:* https://github.com/github/gitignore/blob/main/WordPress.gitignore ; https://notesontech.com/wordpress-gitignore/ ; https://goranstimac.com/blog/git-ignore-for-wordpress-projects/ ; https://doinwp.com/tips/what-to-include-in-gitignore-file-for-wordpress/
- **[media]** Un patrón recomendado es el enfoque 'whitelist': ignorar todo por defecto en el .gitignore y solo permitir explícitamente las carpetas de tema/plugins propios que se quieren versionar, en vez de intentar excluir cada carpeta de terceros una por una.
  - *Fuente:* Resumen de búsqueda web sobre WordPress .gitignore best practices 2026 (belovdigital.agency no se pudo leer directamente, HTTP 403; contenido citado vía snippet de motor de búsqueda, no verificación directa de la página)
- **[media]** Plugins y temas de terceros normalmente se gestionan con Composer (p.ej. vía WPackagist) en vez de commitearlos directamente al repo, para poder reconstruir el entorno desde composer.json/composer.lock sin arrastrar binarios de terceros en el historial git.
  - *Fuente:* Resumen de búsqueda web sobre WordPress Git best practices 2026 (misma fuente belovdigital.agency, no verificada por lectura directa) — no encontré una guía oficial en make.wordpress.org que recomiende Composer explícitamente para este flujo
- **[alta]** Local (by WP Engine) guarda los sitios en la carpeta 'Local Sites' del directorio de usuario; en Windows eso es típicamente C:\Users\<Usuario>\Local Sites\<nombre-sitio>\app\public, y el código propio (tema/plugins) vive dentro de app\public\wp-content.
  - *Fuente:* https://wpengine.com/builders/git-version-control-in-local/ ; https://wpengine.com/support/local/
- **[alta]** Local NO tiene integración de git nativa (ni addon dedicado). Para versionar, hay que usar el botón 'Open Site Shell' (terminal integrado de Local) y ejecutar git init/add/commit manualmente dentro de wp-content.
  - *Fuente:* https://wpengine.com/builders/git-version-control-in-local/
- **[media]** Gotcha documentado de Local: su función de despliegue 'Local Connect' (push del sitio local a hosting) no soporta instalaciones Multisite; para esos casos hay que usar otra vía (p.ej. WP Migrate).
  - *Fuente:* https://wpengine.com/builders/git-version-control-in-local/
- **[alta]** WP-CLI (wp db export / wp db import / wp search-replace) es el flujo estándar para mover el contenido de la base de datos entre entornos (local/staging/producción), y search-replace es necesario porque WordPress serializa arrays PHP en la BD — un UPDATE SQL directo de URLs corrompe esos datos serializados.
  - *Fuente:* https://developer.wordpress.org/cli/commands/search-replace/ ; https://make.wordpress.org/cli/handbook/guides/common-tasks/
- **[media]** Ni WP-CLI db export/import ni los plugins de migración (Duplicator, All-in-One WP Migration, WP Migrate) versionan realmente la base de datos en el sentido de git: producen un volcado/paquete binario completo que se puede sincronizar entre entornos, pero no es diffable ni mergeable — es una herramienta de sincronización de estado, no de historial.
  - *Fuente:* Inferencia razonada a partir de https://developer.wordpress.org/cli/commands/search-replace/ y https://4wp.dev/wp-cli/database/ ; no encontré una fuente que contradiga esto
- **[media]** En 2026, All-in-One WP Migration en su versión gratuita tiene un límite estricto de importación de 512MB, lo que lo hace poco práctico para un sitio maduro con imágenes/vídeo; Duplicator maneja sitios más grandes y permite desplegar directamente en un servidor vacío sin WordPress preinstalado.
  - *Fuente:* https://blog.servmask.com/all-in-one-wp-migration-vs-duplicator/ ; https://duplicator.com/all-in-one-wp-migration-vs-duplicator/
- **[alta]** ACF Local JSON guarda cada grupo de campos (y CPTs, taxonomías, options pages) como archivo JSON en una carpeta acf-json (normalmente dentro del tema, con permisos de escritura), y sincroniza automáticamente: cuando el JSON tiene una fecha de modificación más reciente que la BD (o el item no existe en BD), ACF muestra una pestaña de sincronización en el listado de grupos de campos.
  - *Fuente:* https://www.advancedcustomfields.com/resources/local-json/
- **[media]** Local JSON (guardado y sincronización de grupos de campos) es una función del plugin ACF gratuito, no exclusiva de ACF PRO: la página oficial advancedcustomfields.com/resources/local-json/ no la restringe a PRO, y la ficha del plugin gratuito en wordpress.org tampoco la lista entre las funciones PRO-only (que son Repeater, Flexible Content, Gallery, Clone, Options Pages y ACF Blocks). OJO: si un grupo de campos apunta a una Options Page, esa parte concreta sí requiere PRO (las Options Pages en sí son PRO-only), pero Local JSON como mecanismo no lo es.
  - *Fuente:* https://www.advancedcustomfields.com/resources/local-json/ ; https://wordpress.org/plugins/advanced-custom-fields/ — hay una fuente aislada de foro/blog de terceros que califica Local JSON como 'función PRO', que contradice estas dos fuentes más autorizadas; no pude resolver la contradicción con una fuente 100% definitiva
- **[baja]** El ecosistema ACF está en una situación legal inusual en 2026: tras la disputa Automattic vs WP Engine, WordPress.org publicó un fork gratuito 'Secure Custom Fields' (SCF) con funciones antes exclusivas de PRO liberadas; posteriormente un fallo judicial ordenó devolver el plugin ACF a WP Engine, con más audiencias previstas. El estado exacto y estable del ecosistema ACF/SCF a fecha de hoy no pude confirmarlo con certeza.
  - *Fuente:* https://wptavern.com/wordpress-org-releases-new-secure-custom-fields-plugin-with-acf-pro-features ; https://www.therepository.email/acf-returns-to-wp-engine-after-court-ruling-amid-ongoing-legal-dispute
- **[alta]** Desde WordPress 6.0, los patrones de bloque se pueden registrar colocando archivos PHP con cabecera de metadatos en la carpeta /patterns del tema; WordPress los detecta y registra automáticamente. La documentación oficial recomienda esta ruta de /patterns como la más directa, frente a crear patrones directamente en el editor (que WordPress guarda como custom post type wp_block en la base de datos, con metadato wp_pattern_sync_status).
  - *Fuente:* https://developer.wordpress.org/themes/patterns/registering-patterns/ ; https://developer.wordpress.org/block-editor/reference-guides/block-api/block-patterns/
- **[media]** Los Global Styles de GenerateBlocks (y los 'Global Styles' nativos de WordPress, wp_global_styles) se guardan como custom post type en la base de datos, no como archivo. Existe una herramienta de terceros ('Global Styles Migrator') para exportarlos como JSON, y GenerateBlocks permite exportar vía Tools > Export en el admin, pero automatizar esto en un flujo git requiere desarrollo a medida — no hay sincronización automática de archivo↔BD como en ACF Local JSON.
  - *Fuente:* https://generateblocks.com/new-global-styles-pattern-library/ ; https://snippetclub.com/generateblocks-global-styles-migrator/ ; https://developer.wordpress.org/block-editor/how-to-guides/themes/global-settings-and-styles/
- **[alta]** El consenso de la comunidad es registrar Custom Post Types por código en un plugin propio (plugin site-specific o mu-plugin), no en functions.php del tema: si el registro vive en el tema y el sitio cambia de tema, el contenido del CPT sigue en la base de datos pero deja de ser accesible/editable porque WordPress ya no sabe que ese post type existe.
  - *Fuente:* https://developer.wordpress.org/plugins/post-types/registering-custom-post-types/ ; https://www.wpbeginner.com/opinion/wordpress-custom-post-types-debate-functions-php-or-plugins/ ; https://www.advancedcustomfields.com/blog/creating-custom-post-types-in-wordpress/
- **[media]** Un plugin de UI para registrar CPTs (p.ej. CPT UI) guarda esa configuración en la base de datos, no en archivos de código — por tanto cae en el mismo problema de no ser versionable en git de forma nativa, a diferencia de registrar el CPT directamente en PHP dentro de un plugin propio.
  - *Fuente:* Inferencia razonada a partir de https://developer.wordpress.org/plugins/post-types/registering-custom-post-types/ y la comparación general 'manual vs plugin' en https://www.advancedcustomfields.com/blog/creating-custom-post-types-in-wordpress/; no encontré una fuente que documente explícitamente dónde guarda su configuración cada plugin de UI concreto

### Recomendacion del investigador

Para el próximo proyecto WordPress, monta el repo así: (1) git init dentro de wp-content/ (en Local WP, la ruta en Windows es C:\Users\<Usuario>\Local Sites\<sitio>\app\public\wp-content — usa el 'Open Site Shell' de Local, no hay integración git nativa); (2) versiona solo themes/<tema-hijo>, mu-plugins/ y un plugin propio único para registrar CPTs/taxonomías por código (nunca en functions.php del tema, para que sobrevivan a un cambio de tema); (3) gitignore uploads/, cache, y los plugins de terceros (GenerateBlocks Pro, ACF PRO no están en Packagist público — documenta versiones exactas en un README o composer.json privado en vez de commitear los binarios); (4) activa ACF Local JSON desde ya: crea acf-json/ en el tema hijo y commitea esos archivos — es gratis, no requiere PRO, y resuelve exactamente el punto débil de Aridane (opciones ACF solo en BD); (5) para patrones/secciones reutilizables, decláralos como archivos PHP en /patterns del tema en vez de crearlos solo en el editor (evita que queden atrapados como CPT wp_block en BD); (6) para los Global Styles de GenerateBlocks, que SÍ siguen en BD sin solución nativa de sync, sigue tratando tu CSS complementario como fuente de verdad versionada (tal como ya hiciste en Aridane) y exporta manualmente el JSON de Global Styles como paso de checklist antes de cada entrega, no como algo que git sincronice solo; (7) para mover contenido/BD entre local→staging→producción usa WP-CLI (wp db export + wp search-replace + wp db import) como herramienta de sincronización de entorno, no como historial — no metas los .sql en el repo git; si el hosting del cliente no da acceso WP-CLI, ten Duplicator como plan B (el límite de 512MB gratis de All-in-One WP Migration lo descarta para sitios con imágenes). Ninguna de estas piezas resuelve el problema de fondo (el contenido real de páginas vive en BD y no es versionable), así que sigue dependiendo, como en Aridane, de entregar el marcado de bloques como texto pegable y de tu validador Node — eso seguirá siendo la red de seguridad real.

## contenido-portable

**Resumen.** Investigué en developer.wordpress.org, wp-cli.org/GitHub oficial, y la documentación de bloques cómo mover contenido Gutenberg entre entornos sin romperlo. Los hallazgos confirman y explican técnicamente el fallo del proyecto Aridane: WordPress usa URLs ABSOLUTAS por diseño (no relativas) porque el contenido es "migratorio" -se sindica fuera del sitio-, así que la solución correcta no es escribir rutas relativas sino hacer search-replace de dominio de forma sistemática con wp-cli, protegiendo la columna guid. El punto más crítico técnicamente es el (c): el srcset/sizes de las imágenes en el contenido NO se genera de forma completamente estática en el bloque -se añade en TIEMPO DE RENDERIZADO por wp_filter_content_tags(), que busca la clase wp-image-{ID} en el HTML y busca esa metadata en la base de datos de destino; si el ID no existe ahí, la función degrada silenciosamente (sin error, sin srcset) en vez de romper la build. Para versionar contenido de forma fiable, los Block Patterns como archivos PHP en el tema (carpeta /patterns) son la vía recomendada oficialmente -incluyendo para páginas de inicio completas vía "Template Types: front-page"-, mientras que los Synced Patterns (antes Reusable Blocks) viven solo en la base de datos y una guía de buenas prácticas de una agencia reconocida (10up) desaconseja explícitamente su uso para la mayoría de sitios por esta razón. wp-cli ofrece herramientas concretas (media import --porcelain, search-replace --dry-run --skip-columns=guid) que permiten automatizar un flujo fiable.

### Hallazgos

- **[alta]** WordPress guarda URLs ABSOLUTAS en post_content por diseño intencional (no relativas): 'el contenido es migratorio... puede no mostrarse siempre en el contexto de tu sitio' (RSS, sindicación, microformatos en otras apps). Por tanto la práctica correcta al migrar NO es reescribir a rutas relativas sino ejecutar search-replace de dominio de forma sistemática en cada despliegue.
  - *Fuente:* https://make.wordpress.org/core/handbook/contribute/design-decisions/
- **[alta]** wp-cli search-replace deserializa automáticamente los datos PHP serializados, hace el reemplazo, y re-serializa recalculando las longitudes de byte correctas -por eso NO se debe hacer un SQL UPDATE/REPLACE manual sobre columnas que puedan contener arrays/objetos serializados (theme mods, opciones de plugins, etc.), ya que eso corrompe el string serializado.
  - *Fuente:* https://github.com/wp-cli/search-replace-command/
- **[alta]** --dry-run ejecuta la operación completa y muestra el informe de cuántas filas/columnas cambiarían, sin guardar en BD -es el paso de verificación antes de aplicar el cambio real. Se recomienda además --skip-columns=guid para no tocar la columna guid de wp_posts, ya que WordPress/lectores de feeds la tratan como identificador permanente que no debe cambiar en una migración.
  - *Fuente:* https://developer.wordpress.org/advanced-administration/upgrade/migrating/
- **[alta]** El flag --precise de wp-cli search-replace fuerza el procesamiento vía PHP (en vez de SQL puro) en todas las columnas, más lento pero más fiable para casos de serialización compleja o de bordes (edge cases) donde el reemplazo por SQL directo podría fallar.
  - *Fuente:* https://github.com/wp-cli/search-replace-command/
- **[alta]** El srcset/sizes de las imágenes del contenido NO se genera completa y estáticamente al guardar el bloque: la función núcleo wp_filter_content_tags() se engancha al filtro 'the_content' y actúa en TIEMPO DE RENDERIZADO (no al guardar), buscando en el HTML la clase wp-image-{ID} mediante regex, y usando ese ID para consultar los metadatos del adjunto (_wp_attachment_metadata) en la base de datos del entorno donde se renderiza.
  - *Fuente:* https://developer.wordpress.org/reference/functions/wp_filter_content_tags/
- **[alta]** Si el ID de adjunto de la clase wp-image-{ID} no existe en la base de datos de destino (p. ej. porque el marcado se pegó con un id inventado o de otro entorno, sin subir antes la imagen real), la función NO rompe la build ni lanza error: simplemente omite añadir srcset/sizes para esa imagen concreta, dejando solo el <img src> plano. Esto explica el mecanismo exacto detrás de la pérdida silenciosa de imágenes responsive al migrar marcado con IDs no válidos.
  - *Fuente:* https://developer.wordpress.org/reference/functions/wp_filter_content_tags/
- **[alta]** WordPress reconoce y auto-registra automáticamente cualquier archivo .php colocado en la carpeta /patterns del tema, siempre que tenga una cabecera de comentario PHP válida (Title, Slug con formato namespace/nombre, Categories, y opcionalmente Description, Keywords, Block Types, Post Types, Template Types, Inserter, Viewport Width). Esta es la vía recomendada por el Theme Handbook oficial sobre llamar manualmente a register_block_pattern(), salvo casos excepcionales.
  - *Fuente:* https://developer.wordpress.org/themes/patterns/registering-patterns/
- **[media]** El campo 'Template Types' de un patrón permite asociarlo a una plantilla completa, incluida 'front-page' (portada/home) -no solo a secciones-, y a partir de Gutenberg 15.5 estos patrones aparecen como sugerencias al crear/editar esa plantilla completa en el Site Editor. Es decir, SÍ sirve para versionar una home entera como patrón PHP, no solo fragmentos.
  - *Fuente:* https://developer.wordpress.org/news/2023/04/using-template-patterns-to-build-multiple-homepage-designs/
- **[alta]** Los patrones PHP en el tema son estáticos y versionables en Git (viven como archivo, se despliegan igual en local/staging/producción); los Synced Patterns (antes Reusable Blocks) se guardan como posts del tipo wp_block en la base de datos de cada entorno y deben crearse manualmente en cada uno -no viajan con el código-. Una guía de buenas prácticas de la agencia 10up desaconseja explícitamente el uso de Synced Patterns para la mayoría de sitios por esta fragilidad de despliegue, recomendando patrones PHP o bloques personalizados en su lugar.
  - *Fuente:* https://gutenberg.10up.com/reference/Patterns/synced-patterns/
- **[media]** El endpoint REST de Synced Patterns (WP_REST_Blocks_Controller, /wp/v2/blocks) extiende el controlador estándar de posts y expone el metacampo wp_pattern_sync_status desde WP 6.3 -confirma que técnicamente son posts normales de la BD, no archivos, lo cual es coherente con el punto anterior sobre por qué no viajan entre entornos vía código.
  - *Fuente:* https://developer.wordpress.org/reference/classes/wp_rest_blocks_controller/
- **[alta]** wp media import crea adjuntos reales en la Biblioteca de medios a partir de archivos locales o URLs, y con --porcelain devuelve solo el ID del adjunto creado -pensado explícitamente para uso en scripts (p. ej. wp media import imagen.jpg --porcelain para capturar el ID real y luego construir el bloque con ese ID verdadero, en vez de inventar uno). También soporta --post_id, --featured_image, --alt, --title, --skip-copy.
  - *Fuente:* https://developer.wordpress.org/cli/commands/media/import/
- **[media]** wp import (WXR) tiene un problema documentado de reasignación de imagen destacada tras la importación: los adjuntos pueden no quedar correctamente vinculados a sus posts, lo que confirma que el remapeo de IDs de adjuntos entre entornos es un punto débil conocido incluso en las herramientas oficiales de import/export de WordPress, no solo en flujos de pegado manual de marcado.
  - *Fuente:* https://github.com/wp-cli/import-command/issues/53

### Recomendacion del investigador

Para el nuevo setup, cambiar el flujo de 7 pasos para que: (1) las imágenes del diseño se suban PRIMERO al entorno de destino con 'wp media import ruta/img.jpg --porcelain' (capturando el ID real devuelto), y el marcado de bloques se genere DESPUÉS usando esos IDs reales -nunca IDs inventados en el prototipo-; (2) cualquier movimiento entre entornos pase por 'wp search-replace "http://local.test" "https://dominio.com/subdirectorio" --dry-run --skip-columns=guid' revisado antes de aplicar sin --dry-run, en vez de tocar rutas relativas a mano; (3) las secciones reutilizables (y candidatamente la home entera vía Template Types: front-page) se conviertan en archivos .php dentro de /patterns del tema hijo, versionados en Git, en lugar de Synced Patterns guardados en BD; (4) el validador Node existente se extienda con una regla adicional que compruebe, contra la BD real del entorno destino (vía wp-cli), que cada wp-image-{ID} referenciado en el marcado corresponde a un adjunto que realmente existe -esto habría detectado el fallo del proyecto Aridane antes de pegar en producción, ya que valida ENTORNO, no solo marcado.

## animacion

**Resumen.** Investigación completada con búsqueda web real (agosto 2026). Resumen ejecutivo: (a) GSAP se encola en WordPress con wp_enqueue_script en el functions.php de un tema hijo (más portable/versionable con Git) o vía WPCode (más seguro para quien no toca código, pero vive en la BD y no viaja con el repositorio); GSAP es 100% gratuito desde abril 2025, incluido ScrollTrigger, lo que elimina la fricción de licencia "Club" que existía antes. (b) GenerateBlocks Pro V2 SÍ tiene un panel de "Effects" (opacidad, transform, box/text-shadow, filtros, transiciones) aplicable en hover/focus vía el panel de Selectors, pero confirmé con dos hilos de soporte oficial de GenerateBlocks que NO existe ninguna función nativa de animación por scroll/keyframes — para eso hace falta GSAP. (c) La obligación legal actual (RD 1112/2018 vía EN 301 549 v3.2.1) exige WCAG 2.1 AA; dentro de eso, el criterio 2.2.2 Pausar/Detener/Ocultar (Nivel A) es obligatorio HOY para cualquier animación automática sin interacción; el 2.3.3 Animación por Interacciones es Nivel AAA, no obligatorio, pero conviene implementarlo igual porque EN 301 549 v4.1.1 (que incorpora WCAG 2.2 AA) se espera en el Diario Oficial de la UE hacia octubre de 2026. (d) El punto clave: la animación debe inicializarse DESPUÉS de que el HTML server-rendered (incluidos los query loops) esté en el DOM (en DOMContentLoaded), pero el patrón robusto no es "esperar una vez" sino re-consultar el DOM y llamar a ScrollTrigger.refresh() cada vez que el contenido dinámico cambia de cantidad (filtros AJAX, "cargar más", paginación), en vez de asumir un número fijo de elementos al cargar el script. (e) Rendimiento/CLS: animar solo transform/opacity (nunca top/left/width/height/margin, que son "layout properties"); los scroll shifts NO tienen el margen de gracia de 500ms que sí tienen los clics, así que cualquier animación de scroll mal hecha cuenta directamente contra el CLS.

  - *Fuente:* https://gsap.com/community/forums/topic/41617-scrolltrigger-based-content-changes-and-wordpress-integration/ (respuesta de un moderador en un hilo de foro, no documentación oficial formal)
- **[media]** El escaneo de resize (y por tanto de refresh) de ScrollTrigger está automáticamente debounced a 200ms cuando cambia el viewport, por lo que no hace falta gestionar manualmente el evento resize en la mayoría de casos — pero esto NO cubre cambios de contenido/DOM sin cambio de viewport (ahí sí hace falta refresh() manual o un MutationObserver propio).
  - *Fuente:* resumen de búsqueda agregada sobre GSAP ScrollTrigger, sin fuente primaria única citada verbatim
- **[alta]** Cumulative Layout Shift (CLS): los layout shifts producidos durante un scroll NO reciben la ventana de gracia de 500ms que sí reciben las interacciones discretas (clic, tap, tecla), porque la especificación de Layout Instability excluye explícitamente el scroll como 'excluding input'. Esto significa que cualquier animación de scroll que module propiedades de layout (top, left, width, height, margin, padding, border-width, font-size) generará entradas de layout-shift que cuentan de lleno contra el CLS.
  - *Fuente:* https://www.corewebvitals.io/pagespeed/scroll-triggered-animations-cause-cls
- **[alta]** El patrón correcto para evitar CLS en animaciones (de scroll o de cualquier tipo) es animar exclusivamente transform (translateY/translateX/scale) y opacity, propiedades que se resuelven en el compositor de la GPU y nunca disparan layout shift; existe además una alternativa CSS nativa sin JS, animation-timeline: scroll(), soportada en Chrome/Edge 115+ (no universal en agosto de 2026, hay que comprobar soporte en Safari/Firefox antes de depender de ella en producción).
  - *Fuente:* https://www.corewebvitals.io/pagespeed/scroll-triggered-animations-cause-cls

### Recomendacion del investigador

Patrón concreto para el nuevo setup, punto por punto:

1) DÓNDE ENCOLAR GSAP: crear un tema hijo mínimo (o usar el existente) y encolar gsap.min.js + gsap/ScrollTrigger.min.js AUTO-ALOJADOS (no CDN externo) vía wp_enqueue_script en functions.php, con deps correctas (el script de animación propio depende de ambos) y 'strategy' => 'defer' (WP 6.3+) o in_footer=true. Razón de auto-alojar en vez de CDN: portabilidad entre entornos (staging/producción sin depender de que jsDelivr esté accesible) y evita una dependencia externa en un sitio de ayuntamiento. WPCode es aceptable como alternativa más rápida SOLO si el proyecto no tiene tema hijo versionado en Git; si lo tiene, el tema hijo es más portable porque el código viaja con el repositorio, no con la base de datos.

2) DIVISIÓN DE RESPONSABILIDADES GB vs GSAP: usa el panel Effects/Selectors de GenerateBlocks Pro V2 para micro-interacciones simples de hover/focus (botones, tarjetas) — está confirmado (dos veces, por soporte oficial) que es puramente CSS transition/transform en :hover, sin scroll ni keyframes. Para CUALQUIER animación de entrada al hacer scroll, usa GSAP + ScrollTrigger; no pierdas tiempo buscando una opción nativa de GB para esto, no existe en V2 a fecha de esta investigación.

3) EL PUNTO CLAVE (orden de montaje): inicializa el script de animación en DOMContentLoaded (o el evento equivalente en footer con defer), DESPUÉS de que WordPress haya renderizado en servidor el HTML final, incluidos los query loops. Pero 'esperar una vez' no es suficiente si el contenido puede cambiar de cantidad tras la carga inicial (paginación AJAX, filtros, 'cargar más'): en ese caso, la robustez viene de (a) volver a consultar el DOM (document.querySelectorAll) cada vez que se re-inicializa en vez de cachear una NodeList fija, y (b) llamar a ScrollTrigger.refresh() (con invalidateOnRefresh:true si las posiciones 'from' dependen del contenido) inmediatamente después de que termine la mutación — enganchado al evento de 'terminado' del mecanismo concreto que uses (callback de fetch/AJAX, evento personalizado, o como último recurso un MutationObserver sobre el contenedor del query loop). Nunca asumas un número fijo de tarjetas/posts al cargar el script: es exactamente el tipo de fragilidad que el usuario quiere evitar, análogo a la lección de las rutas de imagen que solo se detectó contra el servidor real y no contra el marcado.

4) ACCESIBILIDAD: implementa gsap.matchMedia() (o un check de window.matchMedia('(prefers-reduced-motion: reduce)')) para servir una versión sin animación (opacity/posición final inmediatas) a usuarios con reducción de movimiento activada. Esto no es opcional legalmente para 2.2.2 (Nivel A, ya exigible), y aunque 2.3.3 (AAA) no es obligatorio hoy bajo EN 301 549 v3.2.1, impleméntalo igual: es la misma línea de código y evita tener que revisar el sitio cuando v4.1.1/WCAG 2.2 AA entre en vigor (previsiblemente ~octubre 2026, aunque esa fecha concreta no está confirmada en fuente primaria).

5) CLS/RENDIMIENTO: anima solo transform y opacity, nunca top/left/width/height/margin/padding. Fija el estado 'antes de animar' (p.ej. opacity:0; transform:translateY(40px)) mediante una clase CSS añadida por un script diminuto e inline en el <head> (para que aplique antes del primer pintado y evite FOUC), y asegúrate de que esa clase quede anulada tanto por prefers-reduced-motion como por un fallback si JS no carga, para que el contenido nunca quede invisible de forma permanente. Verifica con el Performance panel de Chrome DevTools (pista Layout Shifts) que el scroll no genera diamantes morados.

Como en el proyecto de aridane.org, lo más valioso a construir aquí no es la animación en sí sino el patrón de refresh/re-query para contenido dinámico — sin eso, cualquier demo funcionará en local con 6 posts fijos y se romperá en producción en cuanto el query loop devuelva un número distinto de elementos.

## validacion-entorno

**Resumen.** Investigué con búsquedas web reales (agosto 2026) las cuatro capas de validación de entorno que el proyecto Aridane no tuvo: enlaces/imágenes rotas, accesibilidad, rendimiento/peso de imagen y marco legal español. Hay un conjunto maduro de herramientas Node.js/CLI (Lighthouse CI, pa11y-ci, @axe-core/cli, linkinator, wp-cli doctor) que cubren casi todas las comprobaciones de máximo valor y se pueden encadenar en un script de PowerShell sin infraestructura de CI dedicada. El marco legal (RD 1112/2018 + UNE-EN 301549) exige WCAG 2.1 nivel AA hoy mismo para cualquier web de ayuntamiento, con una versión EN 301 549 v4.1.1 (WCAG 2.2 AA) en camino hacia finales de 2026 pero aún no vigente. Diseñé una puerta de calidad de 5 fases (enlaces/imágenes → peso/formato → accesibilidad → Lighthouse/CLS → wp-cli doctor) pensada para bloquear exactamente los dos fallos reales de Aridane: imágenes 404 por ruta relativa y peso de imagen excesivo above-the-fold. Quedan dos huecos que ninguna herramienta cubre de fábrica: comprobar imágenes 404 contra la URL real de producción (con subdirectorio) y verificar breakpoints CSS/JS sincronizados — ambos requieren un script a medida, no una herramienta lista para usar.

### Recomendacion del investigador

Puerta de calidad propuesta, en orden, cada fase bloquea la siguiente si falla (pensada para ejecutarse desde un script PowerShell/Node contra el sitio ya desplegado en staging, con la URL real incluyendo el subdirectorio '/city/' — ese detalle es justamente lo que faltó en Aridane):

FASE 1 — Enlaces e imágenes rotas (bloqueante, coste de montaje bajo, ~10 min): `npx linkinator https://aridane.org/city/ --recurse --concurrency 20` contra la URL de PRODUCCIÓN o staging con el mismo subdirectorio, nunca contra un HTML local suelto — esto es lo único que habría detectado las 11 imágenes 404 de Aridane, porque valida rutas resueltas por el navegador real, no el marcado. Bloquea si hay cualquier 404/500 en <img>, <a> o <link>.

FASE 2 — Peso y formato de imagen (bloqueante, coste bajo): script que recorre las imágenes servidas y falla si alguna above-the-fold supera ~200KB o no está en WebP/AVIF con fallback. Conversión con `npx @squoosh/cli --webp auto --avif auto carpeta/*.{jpg,png}` o sharp-cli antes de subir a producción.

FASE 3 — Accesibilidad WCAG 2.1 AA (bloqueante, coste medio: requiere Node 20/22/24 + Chrome/chromedriver): `pa11y-ci` con `.pa11yci` apuntando a las URLs clave y `standard: WCAG2AA`, complementado con `@axe-core/cli` como segundo motor (cubren contraste, foco visible, orden de tabulación, roles ARIA). Es obligatorio por RD 1112/2018 para un ayuntamiento, no opcional.

FASE 4 — Lighthouse CI (bloqueante, coste medio): `lhci autorun` con `.lighthouserc.json` fijando `cumulative-layout-shift` (maxNumericValue 0.1), LCP (≤2.5s) y el audit de accesibilidad `heading-order` para la jerarquía de encabezados. 3-5 runs para reducir ruido.

FASE 5 — wp-cli doctor (no bloqueante salvo checks críticos, coste bajo si ya se usa wp-cli): valida integridad de core/plugins/temas y tamaño de autoload; añadir un check personalizado en `doctor.yml` para detectar breakpoints CSS/JS desincronizados sería el equivalente a lo que faltó con el desfase de 13px en Aridane — hoy no existe una herramienta lista para esto, hace falta un script propio que extraiga los media-queries del CSS compilado y los compare contra las constantes del JS del carrusel.

Ninguna de estas herramientas sustituye la lección más cara del proyecto Aridane: el validador Node a medida que reconstruye 'css' desde 'styles' en GenerateBlocks. Esa capa (integridad del marcado) y esta capa (integridad del entorno) son complementarias y ambas deben estar en el flujo antes de pegar en producción.

## Addendum verificado el 27/08/2026 — corrige el escapado de comillas

Esta investigación (línea 38 más arriba) daba por buenas **cinco** sustituciones de escape,
incluyendo `"` → `\u0022`, basándose en la lectura de `serialize_block_attributes` de
WordPress. **Es incorrecto y se corrige aquí tras una prueba real, no solo desk research.**

Se creó un post de prueba vía wp-cli, se guardó a través de la API REST (el mismo camino que
usa el editor de bloques al pulsar "Actualizar") en un WordPress real con GenerateBlocks Pro
2.7.0, y se inspeccionó tanto `parse_blocks()` como el CSS final generado en el frontend:

- **Con las comillas escapadas a `\u0022` (las 5 sustituciones), WordPress guarda el
  bloque VACÍO.** El filtro `kses` que sanea el contenido al guardar solo reconoce un comentario
  de bloque como Gutenberg legítimo si el JSON de dentro tiene comillas literales; si no, borra
  silenciosamente todo el interior del comentario. `parse_blocks()` devuelve `attrs: []`.
- **Con solo cuatro sustituciones** (`\u002d\u002d`, `\u003c`, `\u003e`, `\u0026`) **y comillas
  literales**, el bloque sobrevive intacto: `parse_blocks()` decodifica bien, y
  `var(--color-x)` en `styles`/`css` llega tal cual al CSS que GenerateBlocks genera de verdad
  en el frontend (`wp-content/uploads/generateblocks/style-{ID}.css`), sin aplanar a HEX.

Esto también resuelve la pregunta abierta de la línea 40: el riesgo de `--` sin escapar SÍ era
real para marcado pegado a mano (como advertía esta investigación), pero la solución NO era
escapar también las comillas — bastaba con escapar bien los cuatro caracteres que sí rompen el
comentario HTML (`\u002d\u002d`, `<`, `>`, `\u0026`) y dejar las comillas tal cual.

`herramientas/audit-gb.js` (el validador Node del proyecto) nunca exigió el quinto escape —
solo comprueba los cuatro correctos — así que el validador siempre fue correcto; el error estaba
solo en la documentación (`docs/metodo-generateblocks-v2.md` §3, ya corregido) y en esta
investigación. Detalle completo, con la metodología de la prueba, en `ESTADO.md` del repo y en
la memoria `leccion-colores-generateblocks` de Claude Code.
