De cero a publicado

Todo lo que pasa entre no tener nada y tener la web del cliente publicada, en orden, diciendo en cada paso si lo haces tú a mano o se lo pides a Claude.

Antes del paso 1: esto no es un asistente

No hay una pantalla que te lleve de la mano. Abres Claude Code dentro de la carpeta del proyecto y hablas normal: el plugin reconoce de qué va lo que dices y carga solo el método que toca. No hay comandos que memorizar.

Vamos a montar la home del ayuntamiento en GenerateBlocks Este diseño ya está convertido, impórtalo Pásalo a producción

Las tres frases activan partes distintas del plugin sin que nombres ninguna. Solo hay dos atajos que sí se escriben tal cual, y los verás en los pasos 4 y 13: /wp-nuevo-proyecto y /wp-verificar.

Preparación

una vez por ordenador · ~15 min

Esto se hace la primera vez y no se vuelve a tocar nunca, ni aunque cambies de cliente.

  1. A

    Instala Local WP

    a mano

    Es el programa que levanta WordPress en tu ordenador. No instales PHP ni wp-cli por tu cuenta: Local ya los trae dentro y el plugin sabe encontrarlos ahí.

  2. B

    Mete el plugin en Claude Code

    a mano

    Dos líneas en Claude Code, una detrás de otra:

    /plugin marketplace add C:\TRABAJOS\wp-flujo
/plugin install wp-generateblocks@metropolis-wp

    Son dos líneas porque son dos cosas distintas. La primera registra el catálogo — le dice a Claude dónde mirar, sin instalar nada. La segunda coge el plugin de ese catálogo y lo instala. Un catálogo puede contener varios plugins, y por eso el add no se repite aunque mañana empaquetes un segundo flujo.

    Desde ese momento el método está disponible en cualquier carpeta que abras, no solo en esa. Al empezar un proyecto nuevo no escribes nada de esto.

  3. C

    Actualízalo cuando el plugin cambie

    a mano

    Instalar hace una copia del plugin en la carpeta de Claude, no un enlace vivo al repositorio. Editar el repositorio no actualiza lo que Claude carga. Después de un git pull o de tocar una skill, en el terminal:

    claude plugin update wp-generateblocks@metropolis-wp

    Y reinicia Claude Code para que surta efecto. Este es el único comando que se repite en el tiempo — no por proyecto, sino cada vez que el plugin cambia. Si se olvida, sigues trabajando con la versión vieja sin ningún aviso. Para comprobar en qué versión estás: claude plugin list.

El proyecto

de aquí en adelante, una vez por web

El orden importa. Los tres primeros pasos son tuyos y van antes de diseñar nada: si te los saltas, el diseño se cierra a ciegas y luego no encaja.

  1. 01

    Crea el sitio en Local

    a mano

    Nuevo sitio en Local WP, con nombre en minúsculas y guiones (ayto-tazacorte). Arráncalo y entra una vez para comprobar que carga.

    Antes de cerrar Local, apunta el puerto de la base de datos: está en la pestaña Database del sitio, y es un número de cinco cifras como 10011. Lo vas a necesitar en el paso 4.

  2. 02

    Instala GeneratePress y GenerateBlocks Pro

    a mano

    Desde el escritorio de ese WordPress recién creado, como cualquier tema y plugin. Son los dos únicos imprescindibles.

    ⌁ACF, solo si el proyecto lo pide. Hace falta cuando la web lleva contenidos repetibles —noticias, fichas, eventos—. Una landing o una home no necesitan ninguno: instalarlo «por si acaso» es un plugin de más.
  3. 03

    Genera una contraseña de aplicación

    a mano

    En ese WordPress: Usuarios → tu perfil → Contraseñas de aplicación. Le das un nombre, la creas, y copias lo que sale — con los espacios incluidos, tal cual.

    Es lo que permite a Claude preguntarle cosas a WordPress directamente en vez de suponerlas. Sin esto el flujo funciona, pero se queda sin uno de sus controles.

  4. 04

    Arranca el proyecto

    se lo pides

    Abre Claude Code en la carpeta vacía donde vaya a vivir el proyecto y escribe el primero de los dos atajos:

    /wp-nuevo-proyecto "WEB Ayuntamiento de Tazacorte"

    Claude te pregunta las cuatro cosas que no puede adivinar —cómo se llama el sistema de diseño, el identificador corto del proyecto, la carpeta del sitio en Local y ese puerto del paso 1— y monta el esqueleto entero: el contrato de diseño, el tema hijo, las reglas del proyecto y el comprobador.

    ⌁No lo montes tú copiando de otro proyecto. El generador existe precisamente porque hacerlo a mano se olvidaba piezas, y las piezas que se olvidaban eran justo las que fallaban dos semanas después.
  5. 05

    Guarda las credenciales

    se lo pides

    Claude te ofrece hacer el git init y rellenar el fichero de credenciales con la contraseña del paso 3. Ese fichero nunca entra en git, y ya viene configurado para quedarse fuera.

    ⌁La contraseña va entre comillas. Lleva espacios: sin comillas se corta por el primero y luego falla algo que no parece tener nada que ver.
  6. 06

    Congela el contrato de diseño

    se lo pides

    Aquí decides tú: colores, tipografías, tamaños, espaciados. Claude los escribe en un único fichero y genera el CSS a partir de él.

    La regla del sistema es que los nombres se congelan y los valores no. Cambiar el azul del cliente por otro azul es una edición de treinta segundos; cambiar cómo se llama ese color es una migración. Por eso los nombres se piensan una vez, al principio.

  7. 07

    Instala el tema hijo en WordPress

    se lo pides

    Claude copia el tema generado a Local y lo activa. Es el momento en que el contrato deja de ser un fichero tuyo y empieza a existir de verdad en el navegador, y también dentro del editor de WordPress.

    ⌁Antes de activar, mira qué había. Logo, menús y CSS adicional del tema anterior no viajan de un tema a otro. Pídele a Claude que lo compruebe primero si el WordPress no estaba recién hecho.
  8. 08

    Empuja el contrato a los ajustes del tema

    se lo pides

    Un paso corto que evita un problema largo: la paleta que sale en el editor y los márgenes del contenido se rellenan desde los mismos tokens. Así nadie elige a ojo un color parecido en un panel, que es como una web acaba con dos paletas.

  9. 09

    Comprueba en vacío

    se lo pides

    Todavía no hay ni una página, y aun así merece la pena pasar el comprobador: confirma que el contrato está sincronizado y que el tema está puesto. Si algo está torcido, es mucho más barato verlo ahora que con la web entera encima.

  10. 10

    El diseño, y la pregunta obligatoria

    se lo pides

    Le enseñas el diseño —en HTML, un handoff ya convertido, o un Figma que tenga los colores como variables con nombre— y antes de convertir nada Claude te hace una pregunta que no decide solo:

    ¿GenerateBlocks Pro V2 o Gutenberg nativo? La primera llega estilada de una vez y es la vía habitual. La segunda tarda un paso más pero deja la marca en un solo sitio: si el cliente va a mantener la web o reteñirla más adelante, esa gana de calle. Contéstale con lo que sepas del cliente.

  11. 11

    Marcado, validado y publicado

    se lo pides

    Claude genera los bloques, los pasa por dos validadores distintos y los publica en WordPress por línea de comandos. No se copia y pega en el editor: al pegar, WordPress toca el contenido en silencio.

    Tu papel aquí es mirar el resultado y decir qué está mal. Si algo no encaja con el diseño, díselo con palabras normales; el sitio se rehace, no se parchea.

  12. 12

    Animación, si la web la lleva

    se lo pides

    Va al final a propósito, con las páginas ya montadas: animar antes y reorganizar después rompe la animación. Si hay una web de referencia que imitar, dale la dirección — el plugin la mide en vez de suponer cómo se mueve.

  13. 13

    La comprobación de verdad

    a mano

    El segundo y último atajo, ahora con la dirección real de la página ya publicada:

    /wp-verificar http://ayto-tazacorte.local/inicio/

    Este es el paso que más se salta la gente y el único que caza el fallo silencioso favorito de este flujo: que el marcado diga el color y la tipografía correctos, pero el navegador no los reciba. Declarar no es publicar, y sin este paso no se distingue.

  14. 14

    A producción

    se lo pides

    Claude hace el cambio de direcciones en modo ensayo primero, te enseña qué va a cambiar, y solo entonces lo aplica. Las URLs nunca se editan a mano: WordPress las guarda absolutas y repartidas, y a mano siempre queda alguna.

Si algo se tuerce

Díselo con palabras, no busques el comando. «Esto no se ve como el diseño», «el menú no sale en el móvil», «el color no es ese» — el plugin lleva dieciocho fallos silenciosos ya documentados de proyectos anteriores, y varios de esos síntomas los reconoce al vuelo porque ya se pagaron una vez.

Y si vuelves al proyecto días después: cada web generada con esto lleva un ESTADO.md dentro que dice en qué fase se quedó. Empieza por ahí.
